# Feature Specification: 商户回调记录查询

**Feature Branch**: `010-merchant-callback-query`  
**Created**: 2026-05-22  
**Status**: Draft  
**Input**: User description: "本次目的是为了增加菜单商户回调记录查询，因为支付用的最多的接口就是查询和回调，所以当出现商户订单状态和我方订单状态不一致的情况，就需要这个菜单来查询回调记录，所以我认为得有一个回调记录表，和订单是一对一的，然后还有一个回调记录详情表记录调用了多少次，每次的出入参数等。"

## Constitution Compliance *(mandatory)*

在编写规范前，确认本功能涉及的宪法原则：

| 宪法原则 | 是否涉及 | 说明 |
|----------|----------|------|
| I. 模块边界纪律 | 是 | 回调投递发生在收银交易域，查询展示在后台管理域；需明确数据写入与读取职责边界。 |
| II. 支付渠道抽象 | 否 | 本功能针对平台向商户的异步通知，不涉及新增支付渠道或修改渠道回调解析流程。 |
| III. 数据库分区 | 是 | 回调记录属于交易数据，应与订单同属交易库；与渠道入站回调日志区分。 |
| IV. API 响应规范 | 是 | 后台查询接口需返回统一业务结果格式，列表与详情结构清晰可测。 |
| V. 密钥与配置安全 | 是 | 回调报文含签名与商户敏感信息，展示与导出必须脱敏，禁止泄露密钥原文。 |
| 编码规范 | 是 | 后续实现需遵循既有命名与代码组织约定。 |
| 数据库访问规范 | 是 | 涉及列表分页、按订单关联查询、按商户范围过滤。 |
| 安全编码规范 | 是 | 需防止跨商户越权查看回调记录；日志与界面均需脱敏。 |
| 测试规范 | 是 | 需覆盖状态不一致排障场景、多商户隔离、重试多次详情展示，并按影响范围补充端到端验证。 |

> 涉及的原则将在 `plan.md` Constitution Check 中逐项检查。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按订单排查商户回调是否成功 (Priority: P1)

作为平台运营或商户管理员，当发现商户侧订单状态与平台订单状态不一致时，我需要在后台通过订单号或商户订单号快速找到该订单对应的商户回调汇总信息，确认平台是否已发起回调、最近一次结果、累计尝试次数及当前汇总状态，从而判断问题出在平台未通知、通知失败还是商户未正确处理。

**Why this priority**: 这是本功能的核心价值，直接对应「查询 + 回调」最高频的排障路径。

**Independent Test**: 准备一笔已支付且已触发商户回调的订单，以及一笔回调失败且经历重试的订单；在回调记录查询入口按订单号检索，可独立验证汇总信息与订单状态是否一致，无需依赖其他菜单改造。

**Acceptance Scenarios**:

1. **Given** 平台订单已支付且已向商户发起至少一次异步通知，**When** 用户按平台订单号查询回调记录，**Then** 展示与该订单一对一的回调汇总，包含回调类型、目标地址、汇总状态、最近尝试时间及累计尝试次数。
2. **Given** 平台订单尚未触发商户回调（例如未配置回调地址或订单未达通知条件），**When** 用户查询该订单回调记录，**Then** 明确展示「未发起」或等价状态，并说明可读原因（如未配置回调地址），而非空白或报错。
3. **Given** 商户订单号与平台订单号均可定位同一笔订单，**When** 用户使用任一编号查询，**Then** 返回同一笔回调汇总记录。

---

### User Story 2 - 查看每次回调尝试的出入参 (Priority: P1)

作为排障人员，我需要查看该订单每一次向商户发起的回调明细，包括第几次尝试、请求参数、商户响应内容、是否判定为成功、失败原因、耗时及发生时间，以便与商户侧日志比对并定位签名、参数、网络或商户处理逻辑问题。

**Why this priority**: 仅有汇总状态无法解释「为何不一致」；多次重试场景必须能还原每次交互。

**Independent Test**: 对同一订单模拟或构造至少 3 次回调尝试（含成功与失败），打开详情列表即可验证每次记录的出入参、结果与时间顺序，不依赖订单列表页其他字段改造。

**Acceptance Scenarios**:

1. **Given** 某订单累计向商户发起 N 次回调（含自动重试），**When** 用户打开该订单的回调详情，**Then** 按时间顺序展示 N 条明细，每条包含尝试序号、请求摘要、响应摘要、结果状态与耗时。
2. **Given** 某次回调因网络超时或商户返回非成功标识而失败，**When** 用户查看对应明细，**Then** 可看到失败原因分类（如超时、HTTP 错误、业务响应未确认成功）及当时商户返回内容（若有）。
3. **Given** 回调请求参数中包含签名等敏感字段，**When** 用户在界面查看明细，**Then** 敏感字段以脱敏形式展示，完整密钥或可用于伪造请求的信息不可见。

---

### User Story 3 - 在后台菜单中检索与筛选回调记录 (Priority: P2)

作为平台运营人员，我需要在「交易与订单」相关菜单下通过独立入口浏览商户回调记录列表，并按商户、时间范围、回调汇总状态、回调类型（支付/退款等）筛选，以便批量发现近期失败回调并跟进。

**Why this priority**: 不仅支持单笔订单排障，也支持运营巡检与批量发现问题。

**Independent Test**: 在仅启用回调记录菜单与列表查询的情况下，可通过筛选条件得到符合条件的记录集合，并可从列表进入单笔详情。

**Acceptance Scenarios**:

1. **Given** 后台已配置「商户回调记录」菜单入口，**When** 具备权限的用户进入该页面，**Then** 展示分页列表，列至少包含商户、平台订单号、商户订单号、回调类型、汇总状态、最近尝试时间、累计次数。
2. **Given** 用户设置时间范围与汇总状态为「失败」，**When** 执行查询，**Then** 仅返回符合筛选条件的记录，且结果与详情页数据一致。
3. **Given** 用户从列表点击某条记录，**When** 进入详情，**Then** 展示该订单回调汇总及全部尝试明细。

---

### User Story 4 - 从订单上下文跳转查看回调 (Priority: P3)

作为运营人员，我在订单管理或订单详情中处理状态不一致问题时，希望一键跳转到该订单的商户回调记录，减少复制订单号再查询的步骤。

**Why this priority**: 提升排障效率，属于体验增强，可在核心查询能力就绪后交付。

**Independent Test**: 在订单详情存在且该订单已有回调汇总的前提下，通过跳转链接或按钮进入回调详情，订单标识保持一致。

**Acceptance Scenarios**:

1. **Given** 用户在订单相关页面查看某笔订单，**When** 点击「查看商户回调」或等价入口，**Then** 打开该订单对应的回调汇总与明细，无需重新输入订单号。

---

### Edge Cases

- 订单存在但从未配置商户回调地址时，汇总记录应标明未发起原因，明细列表为空且提示明确。
- 同一订单存在支付成功通知与退款结果通知时，应能区分回调类型，避免混在同一业务语义下导致误判（通过类型字段或分开展示）。
- 商户响应体过大时，界面与存储应截断或摘要展示，并保留完整内容可供授权角色按需展开查看（若展开，仍须脱敏）。
- 回调进行中（已发出尚未收到明确成功判定）时，汇总状态应反映「处理中」，避免与最终失败混淆。
- 商户管理员仅可查看本商户（或授权商户）范围内订单的回调记录；跨商户订单号查询必须被拒绝且不泄露是否存在。
- 功能上线前已发生的历史订单，若无留存明细，查询结果应明确为「无记录」而非伪造数据；是否做历史补录不在本规格首版范围。
- 与「渠道入站回调」（支付机构通知平台）区分：本功能仅覆盖平台通知商户，避免运营在排障时查错日志类型。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在平台向商户发起异步通知时，为每笔订单维护一条商户回调汇总记录，与订单一对一关联。
- **FR-002**: 系统必须为每一次向商户发起的回调尝试写入一条明细记录，与汇总记录一对多关联，并记录尝试序号、发生时间、结果状态与耗时。
- **FR-003**: 汇总记录至少包含：所属商户、平台订单号、商户订单号、回调类型、目标回调地址、汇总状态、最近尝试时间、累计尝试次数、最近失败原因摘要（若有）。
- **FR-004**: 明细记录至少包含：请求参数内容（结构化或可读的键值形式）、商户响应内容（若有）、结果判定（成功/失败/处理中）、失败原因分类、HTTP 或业务层状态信息（若可获取）、尝试序号。
- **FR-005**: 系统必须在支付结果通知与退款结果通知（及其他已存在的商户异步通知场景）触发时，同步更新或创建对应类型的回调汇总与明细，不得仅依赖应用日志。
- **FR-006**: 系统必须在后台提供「商户回调记录」菜单入口，归属「交易与订单」业务域，供具备权限的用户查询。
- **FR-007**: 用户必须能够按平台订单号、商户订单号、商户、时间范围、回调类型、汇总状态筛选回调记录列表。
- **FR-008**: 用户必须能够查看单条回调汇总及其全部尝试明细，明细按时间或序号有序展示。
- **FR-009**: 商户管理员只能查询其授权商户范围内的回调记录；系统管理员可按授权查看更广范围。
- **FR-010**: 系统必须在展示与导出中对签名、密钥及类似敏感字段脱敏；不得以明文展示可用于伪造商户请求的秘密信息。
- **FR-011**: 当订单尚无回调汇总时，查询接口应返回明确的空结果或「未发起」状态，不得返回其他订单数据。
- **FR-012**: 系统必须将本功能的回调记录与「渠道入站回调」数据在业务语义上区分，界面文案与筛选维度不得混用，避免排障误导。
- **FR-013**: 列表与详情中的订单状态、回调汇总状态、最近明细结果应可同时展示，便于用户对比「平台订单状态 vs 商户通知内容 vs 通知是否成功」。
- **FR-014**: 系统应支持从订单相关页面跳转到对应回调记录（可在首版之后迭代，但规格保留该能力定义）。

### Key Entities *(include if feature involves data)*

- **商户回调汇总记录**: 表示一笔订单在某一回调类型下的整体通知情况；与订单一对一；关键属性包括商户归属、订单标识、回调类型、目标地址、汇总状态、最近尝试时间、累计次数、最近失败摘要。
- **商户回调明细记录**: 表示一次具体的向商户 HTTP 通知尝试；与汇总记录一对多；关键属性包括尝试序号、请求参数快照、响应快照、结果状态、失败原因、耗时、发生时间。
- **回调类型**: 区分支付结果通知、退款结果通知等业务场景，避免不同通知共用同一汇总语义。
- **汇总状态**: 商户侧通知生命周期的聚合视图，至少包括未发起、处理中、成功、失败等可判定状态。
- **明细结果状态**: 单次尝试的判定结果，与汇总状态逻辑一致且可回溯每一次变化。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在标准排障演练中，运营人员可在 3 分钟内从获知「状态不一致」到定位该订单的最近一次商户回调结果（含成功/失败与响应摘要）。
- **SC-002**: 对于已触发至少一次商户回调的订单，回调汇总记录与订单关联正确率达到 100%（抽样验证无错绑、无遗漏）。
- **SC-003**: 对于经历自动重试的订单，用户可在详情中看到每一次尝试记录，尝试次数与系统实际发起次数一致率达到 100%。
- **SC-004**: 商户管理员跨商户查询测试的阻断率达到 100%，且错误响应不泄露其他商户订单或回调是否存在。
- **SC-005**: 敏感字段在界面展示中的脱敏覆盖率达到 100%（签名及密钥类字段不以明文出现）。
- **SC-006**: 在回调记录菜单中，按时间范围与失败状态筛选后，运营人员可在 5 分钟内找出一批待跟进失败记录并进入详情（以 50 条以内数据集演练为准）。

## Assumptions

- 本功能范围限定为**平台向商户的异步通知**（商户回调），不包含支付机构向平台的入站渠道回调；后者已有独立日志语义，不在本菜单展示。
- 回调汇总与订单为一对一，指「同一订单 + 同一回调类型」一条汇总；若支付与退款通知并存，则通过回调类型区分多条汇总，而非强行合并为一条。
- 首版以**查询与展示**为主，不要求在后台提供「手动重发回调」按钮；若后续需要，将另立规格。
- 功能上线前的历史订单若无持久化明细，默认显示无记录；历史数据补录不在首版交付范围。
- 回调记录保留期限与订单/交易数据保留策略保持一致；未单独约定时默认不少于 90 天，具体保留策略在计划阶段与运维策略对齐。
- 商户数据隔离规则与既有商户隔离治理一致：商户管理员仅本商户，系统管理员可跨商户审计。
- 商户判定回调成功的规则与当前线上一致（例如响应体包含约定成功标识）；本规格不改变成功判定业务规则，仅要求如实记录每次判定结果。
