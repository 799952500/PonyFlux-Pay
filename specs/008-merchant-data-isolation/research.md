# Research: 商户数据隔离治理

## Decision: 采用“商户级 / 全局级 / 系统审计 / 待人工确认”的数据分类基线

**Rationale**: 规格要求既要防止商户间数据混乱，又不能把全局配置强行私有化。分类基线先于代码整改，可避免把公共字典、支付方式类型、菜单模板等全局数据误绑定到商户，也能识别订单、支付、退款、渠道账号、对账差异、风控规则等必须带商户归属的数据。

**Alternatives considered**:
- 全部数据强制绑定商户：会破坏全局配置、平台级菜单和公共渠道定义。
- 仅在页面层过滤：无法覆盖详情、导出、批量、异步、回调、对账等非页面入口。

## Decision: 以后台授权范围作为商户管理员数据边界，系统管理员保留平台级治理能力

**Rationale**: `admin_users` 种子数据已出现 `data_merchant_ids`，说明后台用户存在商户范围授权线索。商户管理员应默认自动限定到授权商户集合，系统管理员可按授权范围跨商户筛选、审计和排障。

**Alternatives considered**:
- 由前端传 `merchantId` 决定范围：容易被篡改，不能作为可信边界。
- 只依赖菜单权限：菜单控制无法防止直接调用接口或导出/批量操作越权。

## Decision: 治理范围覆盖 admin-server、cashier-server、recon-server 与 admin-client

**Rationale**: 现有数据分布在 `payflow_admin`、`payflow_cashier` 与 `recon_*` 表中。后台管理服务同时读取运营配置、交易数据和对账数据；收银服务负责商户签名、订单、支付、退款；对账服务负责账单与差异；后台前端展示列表、详情、统计、导出和配置维护。隔离治理必须覆盖跨模块入口。

**Alternatives considered**:
- 只治理 admin-server：不能覆盖收银端商户接口、回调、退款和对账任务。
- 只治理数据库字段：不能保证所有查询、导出、统计和批量操作都应用授权范围。

## Decision: 将接口契约按“数据范围、治理检查、业务入口、审计反馈”四类记录

**Rationale**: 本功能需要约束 API 行为而不提前指定实现细节。契约应说明商户管理员请求自动受限、系统管理员可带商户筛选、跨商户访问安全拒绝、隔离检查结果可查询、全局配置保持共享。

**Alternatives considered**:
- 为每个现有接口逐一列完整 OpenAPI：当前计划阶段容易冗长，后续任务可按控制器拆分。
- 不写契约：会导致前后端对隔离行为、错误反馈和检查结果字段理解不一致。

## Decision: 验证策略采用多商户样本 + 入口矩阵 + E2E 日志闭环

**Rationale**: 规格成功标准要求至少两个商户，并覆盖列表、详情、统计、导出、批量、异步和全局配置。宪法要求涉及后台页面或跨服务流程时执行 Playwright/Playwright CLI，并监控后台日志至无阻断错误。

**Alternatives considered**:
- 只写单元测试：无法发现前端筛选、接口契约、导出和跨服务问题。
- 只做手工验证：难以稳定复现水平越权和批量边界场景。

## Decision: 存量数据缺失归属时默认进入限制访问或人工确认状态

**Rationale**: 对无法自动推断商户归属的数据，安全默认应是不暴露给普通商户管理员。只有在归属明确或被系统管理员确认后，才能进入正常商户级可见范围。

**Alternatives considered**:
- 默认归属到首个商户或平台商户：会制造新的数据混乱。
- 暂时全部开放：与防止水平越权目标冲突。
