# Feature Specification: 商户数据隔离治理

**Feature Branch**: `008-merchant-data-isolation`  
**Created**: 2026-05-21  
**Status**: Draft  
**Input**: User description: "本次改造主要是实现系统商户之间的数据隔离，防止出现商户之间数据混乱的情况，同时也可以让后台系统方心的交给商户管理员进行运维，所以现在需要检查所有数据，看是否还存在数据没有按照商户进行区分的。当然，有些配置这些适配全局的，就不需要进行商户隔离了"

## Constitution Compliance *(mandatory)*

在编写规范前，确认本功能涉及的宪法原则：

| 宪法原则 | 是否涉及 | 说明 |
|----------|----------|------|
| I. 模块边界纪律 | 是 | 需要覆盖后台管理、收银交易、对账等业务域的数据边界，后续计划阶段需明确各模块职责。 |
| II. 支付渠道抽象 | 是 | 支付渠道账号、路由、订单、退款、回调等数据需要按商户归属隔离，同时全局渠道类型等公共定义保持共享。 |
| III. 数据库分区 | 是 | 需要检查运营配置数据与交易数据中是否存在缺失商户归属或错误跨商户可见的数据。 |
| IV. API 响应规范 | 是 | 涉及后台与商户管理员可访问的数据查询、维护和校验结果展示，响应需保持统一业务结果格式。 |
| V. 密钥与配置安全 | 是 | 商户密钥、渠道账号密钥、回调配置等敏感配置必须限定在所属商户或授权系统角色范围内。 |
| 编码规范 | 是 | 后续整改会涉及查询、校验、权限和数据归属判断，需遵循既有命名与代码组织约定。 |
| 数据库访问规范 | 是 | 需要识别并整改未按商户限定的数据查询、统计、分页、导出和批量操作。 |
| 安全编码规范 | 是 | 需要防止水平越权、日志泄露敏感商户配置、参数绕过商户范围限制。 |
| 测试规范 | 是 | 必须通过隔离场景、跨商户访问拒绝场景、全局配置共享场景验证，并按影响范围补充端到端验证。 |

> 涉及的原则将在 `plan.md` Constitution Check 中逐项检查。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 商户管理员只能运维本商户数据 (Priority: P1)

作为商户管理员，我需要在后台系统中只能查看、维护、统计和导出自己所属商户的数据，避免看到或误操作其他商户的订单、支付、退款、渠道账号、对账差异和业务配置。

**Why this priority**: 这是本次改造的核心价值，直接决定后台系统能否放心交给商户管理员使用，并防止商户间数据混乱和水平越权。

**Independent Test**: 准备至少两个商户及各自的数据，使用其中一个商户管理员登录后台，逐项访问列表、详情、统计、导出、编辑、删除、审核等操作，确认只能触达本商户数据，直接使用其他商户数据标识也无法读取或修改。

**Acceptance Scenarios**:

1. **Given** 系统存在商户 A 和商户 B 的订单、支付、退款、渠道账号和对账数据，**When** 商户 A 管理员查看相关页面或发起查询，**Then** 结果中只出现商户 A 数据。
2. **Given** 商户 A 管理员已知商户 B 的某条业务数据标识，**When** 通过详情、编辑、审核、导出或批量操作尝试访问该数据，**Then** 系统拒绝访问或返回无可操作数据，且商户 B 数据不被泄露或变更。
3. **Given** 商户 A 管理员查看汇总看板、趋势图或统计指标，**When** 系统展示金额、笔数、成功率、差异数等汇总结果，**Then** 统计范围仅包含商户 A 数据。

---

### User Story 2 - 系统管理员可进行全局治理与跨商户审计 (Priority: P1)

作为系统管理员，我需要保留跨商户运维、审计、排障和配置治理能力，同时能够明确识别哪些数据属于商户级、哪些数据属于全局级，避免整改后影响平台侧管理能力。

**Why this priority**: 平台仍需承担统一运营与问题排查职责，隔离不能导致系统管理员无法管理全局配置或无法定位跨商户问题。

**Independent Test**: 使用系统管理员账号查看商户级数据、全局配置、跨商户统计和审计入口，确认系统管理员可按授权查看全量或指定商户范围，并能区分全局配置与商户数据。

**Acceptance Scenarios**:

1. **Given** 系统管理员进入后台管理功能，**When** 查看商户级数据列表，**Then** 可以按商户筛选并识别每条数据的商户归属。
2. **Given** 某项配置被定义为全局配置，**When** 系统管理员查看或维护该配置，**Then** 该配置不强制绑定单一商户，并对所有适用商户保持一致可用。
3. **Given** 系统管理员需要排查跨商户异常，**When** 查看统计、日志或审计结果，**Then** 可以在授权范围内按商户维度定位问题，而不会混淆数据归属。

---

### User Story 3 - 发现并治理历史数据隔离缺口 (Priority: P2)

作为平台运维人员，我需要检查现有数据和功能入口，识别哪些数据缺少商户归属、哪些查询或操作没有按商户限制，并形成可执行的整改结果，避免历史遗留数据继续造成混乱。

**Why this priority**: 仅控制新增访问不足以解决存量风险，必须识别历史数据缺口和未隔离入口，才能达到可交付给商户管理员运维的安全基线。

**Independent Test**: 针对所有业务数据清单执行隔离检查，输出商户级、全局级、需补充归属、需人工确认四类结果，并验证整改后跨商户访问测试全部通过。

**Acceptance Scenarios**:

1. **Given** 系统存在多类业务数据和配置数据，**When** 执行隔离检查，**Then** 每类数据都被标记为商户级、全局级或需人工确认，并说明理由。
2. **Given** 某类数据应属于商户级但缺少商户归属，**When** 完成治理，**Then** 该数据具备明确归属或被列入人工处置清单，且不会继续被普通商户管理员跨商户访问。
3. **Given** 某个功能入口此前未按商户过滤，**When** 完成整改验证，**Then** 该入口对商户管理员只返回本商户范围内的数据。

---

### Edge Cases

- 业务数据缺少商户归属且无法自动推断时，系统必须将其列入人工确认或隔离待处理范围，不得默认暴露给任一商户管理员。
- 全局配置被商户管理员访问时，系统必须只允许查看或使用与其权限匹配的全局信息，不得泄露其他商户的密钥、账号或业务数据。
- 商户管理员通过 URL、请求参数、导出任务、批量操作、统计筛选、搜索条件或历史缓存指定其他商户标识时，系统必须阻止跨商户读取或变更。
- 系统管理员切换商户筛选条件时，统计结果、列表结果和导出结果必须保持同一商户范围，不得混入上一次查询范围的数据。
- 数据被软删除、冻结、停用或归档后，仍必须保留可验证的商户归属，避免通过历史查询绕过隔离。
- 异步处理、回调、对账、补单、退款审核等非页面入口也必须保持商户归属一致。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须对所有业务数据进行归类，至少区分为商户级数据、全局配置数据、系统审计数据和需人工确认数据。
- **FR-002**: 系统必须为商户级数据建立明确的商户归属，并在查看、搜索、详情、统计、导出、创建、更新、删除、审核、批量操作和异步处理时持续应用该归属限制。
- **FR-003**: 商户管理员必须只能访问其所属商户或被明确授权商户范围内的数据。
- **FR-004**: 商户管理员不得通过手动传入其他商户标识、业务数据标识、分页条件、导出条件或批量操作项读取或修改其他商户数据。
- **FR-005**: 系统管理员必须能够在授权范围内跨商户查看和治理数据，并能按商户筛选、定位和审计商户级数据。
- **FR-006**: 系统必须保留全局配置的共享属性，对确认为全局适用的数据不得强制绑定单一商户。
- **FR-007**: 系统必须为全局配置和商户级配置提供清晰区分，避免商户管理员误认为全局配置属于自己或能够影响其他商户。
- **FR-008**: 系统必须识别缺少商户归属但应按商户隔离的数据，并阻止其继续向普通商户管理员无差别暴露。
- **FR-009**: 系统必须提供数据隔离检查结果，覆盖数据类别、归属状态、风险等级、影响入口、整改状态和是否需要人工确认。
- **FR-010**: 系统必须覆盖交易链路相关数据，包括订单、支付、退款、回调、渠道账号、渠道路由、商户配置、对账任务、对账文件、对账记录和差异处理。
- **FR-011**: 系统必须覆盖后台运维相关数据，包括用户、角色、权限、菜单、操作日志、登录记录、统计看板、导出任务和审核任务，并明确哪些属于商户级、哪些属于平台级或全局级。
- **FR-012**: 系统必须保证新增商户级数据在创建时具备正确商户归属，且归属不能被普通商户管理员伪造或改写。
- **FR-013**: 系统必须在跨商户访问被拒绝时给出安全、明确的业务反馈，不暴露目标数据是否存在、敏感字段或其他商户信息。
- **FR-014**: 系统必须记录商户管理员对商户级数据的关键操作审计信息，审计信息至少能支持定位操作者、操作对象、所属商户、操作结果和时间。
- **FR-015**: 系统必须验证所有商户隔离整改结果，至少覆盖多商户列表隔离、详情隔离、统计隔离、导出隔离、批量操作隔离、异步任务隔离和全局配置共享场景。

### Key Entities *(include if feature involves data)*

- **商户**: 平台中的业务主体，是商户级数据隔离的归属边界。
- **商户管理员**: 被授权运维一个或多个商户数据的后台用户，其可见和可操作范围必须由商户授权决定。
- **系统管理员**: 平台侧运维人员，可在授权范围内管理全局配置、跨商户审计和数据治理。
- **商户级数据**: 与单个商户业务直接相关的数据，例如订单、支付、退款、渠道账号、商户配置、对账任务和业务审核记录。
- **全局配置数据**: 对平台或多个商户统一适用的数据，例如公共字典、基础渠道类型、系统级菜单模板、通用规则或其他被明确认定为全局的配置。
- **数据隔离检查项**: 对某类数据或功能入口的检查结果，包含数据类别、是否需要商户归属、当前归属状态、风险等级、影响范围和整改状态。
- **授权范围**: 用户可访问的商户集合或平台级权限集合，用于决定数据查询、操作和审计范围。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 针对已纳入清单的商户级数据入口，商户管理员跨商户读取或修改测试的阻断率达到 100%。
- **SC-002**: 所有纳入治理范围的数据类别均完成分类，分类结果覆盖率达到 100%，且每类数据都有商户级或全局级判定依据。
- **SC-003**: 对至少两个商户的隔离验收中，列表、详情、统计、导出、批量操作和异步处理场景均不出现其他商户数据。
- **SC-004**: 需人工确认的数据项全部形成处置清单，且在处置完成前对普通商户管理员不可见或不可操作。
- **SC-005**: 系统管理员能够在 3 分钟内定位任一商户级数据的商户归属、风险状态和最近关键操作记录。
- **SC-006**: 被认定为全局配置的数据在隔离整改后仍可被适用范围内的商户正常使用，且不会泄露商户专属敏感信息。
- **SC-007**: 商户管理员完成日常运维任务时，90% 以上的常用页面无需人工选择商户即可自动限定到授权范围。

## Assumptions

- 商户管理员默认只能管理其所属或被明确授权的商户范围；系统管理员默认具备平台级治理能力，但仍受角色权限控制。
- 数据隔离的首要目标是防止商户之间数据混淆和水平越权，不要求将所有全局配置改造成商户私有配置。
- 全局配置包括不携带单一商户业务归属、且对平台或多商户统一适用的数据；若配置包含商户专属密钥、账号、费率或回调信息，则应视为商户级数据。
- 历史数据若无法自动判断归属，应优先进入人工确认或限制访问状态，而不是默认归属于任一商户。
- 本功能关注业务可见性、操作权限和数据归属治理；具体技术方案、表结构调整和代码改动将在后续计划阶段确定。
