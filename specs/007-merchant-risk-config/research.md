# Phase 0 Research: 商户级风控配置

## Decision: 风控配置以 admin 库为权威源，cashier 执行侧读取适用规则快照

**Rationale**: 现有后台风控配置位于管理端，支付请求在 `payflow-cashier-server` 的订单创建前执行风控。以 admin 库作为配置权威源符合运营配置归属，执行侧通过现有配置刷新机制或规则镜像获得可评估规则，避免 cashier 直接承担后台配置管理职责。

**Alternatives considered**:
- 仅在 cashier 库维护全部风控配置：会把管理后台配置职责下沉到支付服务，弱化模块边界。
- admin 与 cashier 双写完全独立配置：一致性复杂度高，容易出现后台可见配置与实际执行配置不一致。

## Decision: 规则归属与作用范围分离建模

**Rationale**: 规则归属用于表达谁创建和管理规则（平台或商户），作用范围用于表达平台规则适用于全商户还是指定商户。二者分离后可以明确支持：平台全商户、平台定向商户、商户自建仅自己三种规则，权限判断也更清晰。

**Alternatives considered**:
- 在规则表上只加一个 `merchant_id`：无法同时表达平台全局、平台定向多商户和商户自建三种语义。
- 使用逗号分隔商户 ID 存在规则表字段：查询、索引、权限校验和维护成本高，不利于分页筛选。

## Decision: 平台定向范围使用独立关联实体

**Rationale**: 平台规则可作用于多个商户，独立关联实体便于按商户查询适用规则、统计范围数量、校验空范围，并避免单字段拼接造成 SQL 注入或索引失效问题。

**Alternatives considered**:
- JSON 字段存储 merchantId 列表：读写简单但检索和约束弱，无法高效按商户筛选。
- 每个商户复制一条规则：配置变更需要批量同步，审计和规则身份会混乱。

## Decision: 商户自建规则的 merchantId 从认证上下文派生

**Rationale**: 商户用户不能信任请求体传入的 merchantId。创建、查询、修改、启停、命中记录查看均应从认证上下文获取当前商户身份，服务端强制过滤和赋值，保证水平越权 100% 被拒绝。

**Alternatives considered**:
- 前端隐藏 merchantId 选择框：只能改善体验，不能形成安全边界。
- 请求体允许传 merchantId 并在前端限制：易被伪造，不符合安全编码要求。

## Decision: 支付请求只评估当前商户适用的启用规则

**Rationale**: 现有 `RiskRuleService.listEnabledRules()` 返回全部启用规则，会导致全局性评估。需要改为按当前 merchantId 返回：平台全商户规则、平台定向该商户规则、该商户自建规则，并按优先级和 ID 稳定排序。

**Alternatives considered**:
- 继续加载所有规则后在内存中过滤：规则规模变大后性能差，也容易遗漏权限过滤。
- 每个规则执行时再判断适用范围：执行链路复杂，命中记录上下文不集中。

## Decision: 多规则命中采用确定性裁决并记录命中上下文

**Rationale**: 当同一请求命中多条规则时，用户需要可解释结果。执行侧按优先级排序，拦截动作优先于非拦截动作；最先决定拦截的规则作为返回原因，同时记录可追踪命中信息。若后续需要全量命中列表，可在执行服务中扩展为收集后裁决。

**Alternatives considered**:
- 任意一条先查到先拦截：结果受数据库返回顺序影响，不可预测。
- 所有规则都评估后统一裁决：解释性最好，但对实时支付请求成本更高，可作为后续优化。

## Decision: 阈值金额统一使用 Long 分，禁止元/分浮点转换

**Rationale**: 项目宪法已明确金额和风控阈值必须用 Long 分，历史优化报告也指出 BigDecimal 元比较存在精度风险。新设计中规则阈值、支付金额和累计金额均以分为单位进行比较。

**Alternatives considered**:
- 保持 `DECIMAL(18,2)` 表示元：会延续历史精度和转换问题。
- 前端传元、后端转换：可以作为展示层行为，但存储和契约必须明确以分为准。

## Decision: 配置变更和命中记录纳入审计查询

**Rationale**: 风控规则属于影响支付结果的高敏运营配置，需要知道谁改了规则、何时生效、哪些请求被拦截。管理员可查看全部，商户只查看自己相关记录，支持误杀排查与合规追踪。

**Alternatives considered**:
- 仅依赖普通操作日志：难以表达规则变更前后摘要和命中上下文。
- 仅记录拦截失败消息：无法支持后台筛选、统计和审计。

## Decision: API 契约按管理员与商户端分层

**Rationale**: 管理员需要跨商户筛选和维护平台规则；商户需要自助管理自己的规则。分层契约可以避免在同一接口中混合大量权限分支，也更容易测试越权场景。

**Alternatives considered**:
- 单一 `/admin/risk/rules` 接口根据角色分支：实现可行，但契约语义混乱，商户端误用风险高。
- 仅提供管理员接口，商户通过管理员代配：不满足商户自助配置需求。
