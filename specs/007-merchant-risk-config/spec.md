# Feature Specification: 商户级风控配置

**Feature Branch**: `007-merchant-risk-config`
**Created**: 2026-05-20
**Status**: Draft
**Input**: User description: "支付后台系统有一个风控配置功能，他能根据系统的实时性来拦截异常支付请求，但是目前只是全局性的，我想把他做成一个商户性质的，也就是管理员可以看到所有的配置，并且 管理员配置的风控可以作用于所有商户，也可以作用于部分商户，但是商户自己配置的风控就只能作用于自己。请给出方案"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员配置全局或定向风控 (Priority: P1)

管理员进入风控配置管理页面，能够查看所有风控配置，并创建、编辑、启停由平台管理的风控规则。管理员创建规则时可以选择规则作用于所有商户，也可以选择仅作用于一个或多个指定商户，从而统一治理平台风险并支持对高风险商户定向收紧策略。

**Why this priority**: 这是从全局风控升级为商户级风控的核心能力，直接决定平台能否同时支持统一策略和差异化治理。

**Independent Test**: 可以通过管理员账号创建一条作用于所有商户的规则和一条仅作用于指定商户的规则，分别用不同商户发起支付请求，验证规则可见性、适用范围和拦截结果。

**Acceptance Scenarios**:

1. **Given** 管理员已登录且存在多个商户，**When** 管理员创建一条适用于所有商户的启用风控规则，**Then** 所有商户的符合条件支付请求都会被该规则评估。
2. **Given** 管理员创建一条仅适用于商户 A 和商户 B 的启用风控规则，**When** 商户 C 发起符合该规则条件的支付请求，**Then** 商户 C 不会因该定向规则被拦截。
3. **Given** 管理员查看风控配置列表，**When** 列表加载完成，**Then** 管理员能看到平台规则和各商户自建规则，并能按商户、作用范围、状态、规则类型筛选。

---

### User Story 2 - 商户配置仅对自己生效的风控 (Priority: P1)

商户用户进入自己的风控配置页面，只能查看、创建、编辑、启停归属于自己的风控规则。商户自建规则只对该商户的支付请求生效，不能选择其他商户，也不能修改平台规则。

**Why this priority**: 保障商户自治能力，同时避免水平越权和跨商户误拦截，是商户级隔离的必要边界。

**Independent Test**: 可以通过商户 A 创建一条自建规则，再分别以商户 A 和商户 B 发起相同特征支付请求，验证仅商户 A 被规则评估或拦截，并验证商户 B 无法查看或修改该规则。

**Acceptance Scenarios**:

1. **Given** 商户 A 已登录，**When** 商户 A 创建一条启用的自建风控规则，**Then** 该规则的归属商户为商户 A，且作用范围固定为商户 A。
2. **Given** 商户 B 已登录，**When** 商户 B 查询风控配置列表，**Then** 不会看到商户 A 的自建风控规则。
3. **Given** 商户 A 尝试将自建规则作用于其他商户，**When** 提交配置，**Then** 系统拒绝该操作并提示无权配置其他商户。

---

### User Story 3 - 支付请求按适用范围实时评估 (Priority: P1)

当商户发起支付请求时，系统根据请求所属商户，只加载并评估对该商户生效的风控规则，包括平台全商户规则、平台定向到该商户的规则、该商户自建规则。任一启用规则命中拦截条件时，支付请求会被拒绝并返回可理解的风控拦截原因。

**Why this priority**: 风控配置的最终价值体现在支付请求实时拦截，必须保证配置范围与执行结果一致。

**Independent Test**: 准备三类规则：平台全局、平台定向、商户自建；针对同一支付请求特征验证每类规则仅在其适用商户下触发，并产生命中记录。

**Acceptance Scenarios**:

1. **Given** 商户 A 存在平台全商户规则、平台定向规则和商户自建规则，**When** 商户 A 发起符合三条规则条件的支付请求，**Then** 系统会评估这些规则并按规则优先级返回拦截结果。
2. **Given** 商户 C 不在某平台定向规则适用范围内，**When** 商户 C 发起符合该规则条件的支付请求，**Then** 系统不会使用该定向规则拦截商户 C。
3. **Given** 支付请求被风控规则拦截，**When** 用户查看支付结果或后台命中记录，**Then** 能看到拦截发生、命中规则、规则来源和归属范围。

---

### User Story 4 - 审计和排查风控命中 (Priority: P2)

管理员需要查看所有商户的风控命中记录，用于风险分析、误杀排查和策略优化。商户用户只能查看自己支付请求产生的风控命中记录，了解哪些自建规则或平台规则影响了自己的交易。

**Why this priority**: 没有命中可追踪性，风控策略难以运营和解释；但它依赖规则配置与执行先正确落地。

**Independent Test**: 通过不同来源规则触发拦截后，分别用管理员和商户账号查看命中记录，验证可见范围与记录内容。

**Acceptance Scenarios**:

1. **Given** 多个商户产生风控命中记录，**When** 管理员查看命中记录列表，**Then** 管理员能看到全部记录并按商户、规则来源、时间和结果筛选。
2. **Given** 商户 A 产生风控命中记录，**When** 商户 B 查看命中记录，**Then** 商户 B 不会看到商户 A 的记录。

### Edge Cases

- 当同一支付请求同时命中平台规则和商户自建规则时，系统必须给出确定的拦截结果，并记录所有已命中的规则或至少记录最终拦截规则及可追踪上下文。
- 当管理员删除或停用某条平台规则时，该规则必须不再影响后续支付请求，历史命中记录仍可查询。
- 当商户被禁用、删除或状态异常时，归属于该商户的自建规则不得影响其他商户，管理员仍应能查看历史配置和命中记录。
- 当平台定向规则的适用商户列表为空时，系统必须阻止启用或要求明确改为全商户范围，避免产生含义不明的规则。
- 当商户没有任何自建规则时，支付请求仍需评估对其生效的平台规则。
- 当规则配置变更与支付请求并发发生时，系统必须保证单次支付请求使用一个一致的规则快照，避免部分新旧配置混用。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持风控规则的归属来源，至少区分平台规则和商户自建规则。
- **FR-002**: 系统必须支持平台规则配置作用范围，作用范围包括所有商户和指定商户集合。
- **FR-003**: 系统必须限制商户自建规则的作用范围固定为该商户自身，不允许商户选择、查看、影响其他商户。
- **FR-004**: 管理员必须能够查看所有风控配置，包括平台规则和所有商户自建规则。
- **FR-005**: 管理员必须能够按商户、规则来源、作用范围、启用状态、规则类型和更新时间筛选风控配置。
- **FR-006**: 管理员必须能够创建、编辑、启用、停用平台规则，并维护指定商户范围。
- **FR-007**: 管理员必须能够查看商户自建规则，但对商户自建规则的修改权限必须有明确限制和审计记录。
- **FR-008**: 商户用户必须只能查看、创建、编辑、启用、停用归属于自己的自建规则。
- **FR-009**: 商户用户必须不能创建平台规则，不能将规则设置为全商户范围或指定其他商户范围。
- **FR-010**: 支付请求风控评估时，系统必须只评估对当前请求商户生效且处于启用状态的规则。
- **FR-011**: 对某商户生效的规则集合必须包含平台全商户规则、平台定向到该商户的规则、该商户自建规则。
- **FR-012**: 当支付请求命中拦截条件时，系统必须拒绝该请求，并返回不泄露敏感策略细节的风控拦截提示。
- **FR-013**: 系统必须记录风控命中结果，包含请求商户、命中规则、规则来源、规则作用范围、处理结果、发生时间和可用于排查的请求摘要。
- **FR-014**: 管理员必须能够查看全部风控命中记录，商户用户必须只能查看自己商户的命中记录。
- **FR-015**: 系统必须记录风控配置的关键变更审计，包含操作者、操作时间、变更对象、变更类型和变更前后摘要。
- **FR-016**: 系统必须在启用规则前校验规则条件完整性、作用范围有效性和权限边界。
- **FR-017**: 系统必须支持规则优先级或确定性裁决方式，确保多条规则同时命中时结果可预测、可解释。
- **FR-018**: 系统必须保证已停用规则不参与后续支付请求评估，但历史命中记录和审计记录不被删除。

### Key Entities

- **风控规则**: 表示一条可评估支付请求风险的配置，关键属性包括规则名称、规则类型、规则条件、处理动作、启用状态、优先级、归属来源、归属商户、创建人和更新时间。
- **规则作用范围**: 表示平台规则适用于哪些商户，关键属性包括范围类型（所有商户或指定商户）、商户集合和生效状态。
- **商户**: 表示支付请求的业务归属方，也是商户自建规则和定向平台规则的适用对象。
- **支付请求**: 表示待风控评估的支付发起行为，关键属性包括请求商户、金额、支付方式、请求时间、设备或环境摘要、支付账户相关摘要和请求状态。
- **风控命中记录**: 表示一次支付请求被规则评估命中的结果，关键属性包括请求商户、命中规则、命中原因摘要、处理结果、发生时间和追踪标识。
- **风控变更审计**: 表示规则配置生命周期中的关键操作记录，关键属性包括操作者、角色、操作类型、目标规则、变更摘要和操作时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员能够在 2 分钟内完成一条平台全商户规则或平台定向商户规则的创建、启用和验证。
- **SC-002**: 商户用户能够在 2 分钟内完成一条仅对自己生效的风控规则创建、启用和验证。
- **SC-003**: 在包含至少 100 个商户和 1,000 条启用规则的场景下，95% 的支付请求能在用户无明显等待感的情况下完成风控评估并返回放行或拦截结果。
- **SC-004**: 权限边界测试中，商户跨商户查看、创建、修改、启停规则和查看命中记录的尝试 100% 被拒绝。
- **SC-005**: 平台全商户规则、平台定向规则、商户自建规则三类规则的适用范围测试通过率达到 100%。
- **SC-006**: 风控拦截产生的命中记录在 1 分钟内可被具备权限的用户查询到，且记录包含排查所需的核心上下文。
- **SC-007**: 管理员和商户用户在首次使用风控配置页面时，关键任务完成率达到 90% 以上。

## Assumptions

- 管理员指平台后台管理员，具备跨商户管理权限；商户用户指归属于单个商户的运营或管理人员。
- 本功能沿用现有风控规则类型和规则条件表达能力，不在本阶段扩展新的风控算法或机器学习能力。
- 风控规则默认只执行拦截或放行类决策；告警、人工审核等动作若已有能力可复用，否则不纳入本阶段核心范围。
- 管理员可以查看所有配置和记录，但对商户自建规则的直接修改应被审计，并在界面上明确标识为代操作或平台干预。
- 商户自建规则的优先级不得绕过平台规则；当平台规则和商户规则冲突时，以更严格或更高优先级的拦截结果为准。
- 支付请求的商户身份在进入风控评估前已被可靠识别和认证。
