# Feature Specification: 收银台国际化（简体中文 / 繁体中文 / 英文）

**Feature Branch**: `015-cashier-i18n`
**Created**: 2026-06-03
**Status**: Draft
**Input**: User description: "本次旨在给收银台增加国际化支持，支持的语言包含简体中文，繁体中文和英文，根据项目代码和内容输出开发计划"

## 现状分析 *(context)*

**前端（`payflow-cashier-client`）已有 i18n 基线**：已集成 `vue-i18n@11`，`src/i18n.ts` 已创建实例并含 `zh-CN`、`en-US` 两套键对齐语言包，页面组件均通过 `$t()` / `useI18n()` 取文案（`.vue` 中无硬编码中文），语言偏好持久化于 `localStorage`（键 `payflow-cashier-locale`），默认与回退均为 `zh-CN`。Element Plus 语言仅在启动时一次性设置，不支持运行时切换。**缺口**：缺繁体中文（`zh-TW`）语言包。

**下单接口（`payflow-cashier-server`）**：`CreateOrderRequest` 当前**无语言字段**，包含 `subject`/`body` 等商户提供文本。需新增展示语言参数。

**后台支付方式配置（`payflow-admin-server` + `payflow-admin-client`）**：实体 `PaymentMethod`（表 `admin_payment_methods`）的 `methodName`、`description` 均为**单语言单列**。需扩展为三语存储与三语录入。

## Clarifications

### Session 2026-06-03

- Q: 结算/收据等订单相关页面是否完全移除用户语言切换器，语言仅由下单接口 language 参数决定？ → A: 是，完全移除切换器，订单页语言仅由下单接口 `language` 参数决定。
- Q: 不绑定订单的门户页面（登录/入驻申请/入驻结果查询）语言如何决定？ → A: 保留浏览器自动判定 + 手动切换器。
- Q: 后台多语言配置覆盖哪些字段？ → A: 支付方式的展示名 `methodName` 与描述 `description`（三语）。
- Q: 后台多语言文案的存储方式？ → A: 在现有 `admin_payment_methods` 表增加 per-language 列（如 `method_name_zh_cn` / `method_name_zh_tw` / `method_name_en`，描述同理）。
- Q: 翻译完整性与回退策略？ → A: 三种语言全部必填，禁止保存不完整译文。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 收银台按下单语言展示 (Priority: P1)

商户在调用下单接口时传入展示语言（简体中文 / 繁体中文 / 英文），付款人进入收银台（PC/H5）及电子收据页时，界面即以该语言呈现；收银台不提供用户可见的语言切换器，付款人无法手动改变订单页语言。

**Why this priority**: 这是本次国际化的核心交付——让商户控制其顾客看到的支付语言，是其余能力的基础。

**Independent Test**: 用 `language=en-US` 创建订单并打开收银台，验证全部页面文案（导航、金额标签、支付方式名、按钮、提示）为英文且页面无任何语言切换入口；改用 `language=zh-TW` 重新下单验证为繁体。

**Acceptance Scenarios**:

1. **Given** 商户下单时传 `language=zh-TW`, **When** 付款人打开收银台, **Then** 收银台与收据页全部静态文案以繁体中文展示，且页面无语言切换器。
2. **Given** 商户下单时传 `language=en-US`, **When** 付款人打开收银台, **Then** 界面以英文展示，Element Plus 内置组件文案亦为英文。
3. **Given** 商户下单未传 `language` 或传入不支持的值, **When** 付款人打开收银台, **Then** 界面回退为默认简体中文（`zh-CN`），流程不报错。
4. **Given** 收银台订单页, **When** 付款人查找语言切换入口, **Then** 页面不存在任何用户可见的语言切换控件。

---

### User Story 2 - 三语全量静态文案覆盖 (Priority: P1)

收银台所有用户可见静态文本（PC/H5 收银主页面、二维码弹窗、支付结果、电子收据、商户登录、入驻申请、入驻结果查询、错误与提示消息、路由页面标题、支付方式与渠道展示名）在三种语言下均有完整、准确、无遗漏的翻译。

**Why this priority**: 任一界面残留未翻译文案或键名占位符，会直接破坏国际化体验。

**Independent Test**: 在三种语言下遍历全部页面与弹窗，确认无未翻译文本、无键名泄漏（如 `cashier.title`）、无语言混杂。

**Acceptance Scenarios**:

1. **Given** 简体中文, **When** 遍历全部页面与弹窗, **Then** 所有文案为简体中文且无键名泄漏。
2. **Given** 繁体中文, **When** 遍历全部页面与弹窗, **Then** 所有文案为符合繁体习惯的繁体中文（如"支付寶"而非"支付宝"）。
3. **Given** 英文, **When** 遍历全部页面与弹窗, **Then** 所有文案为通顺、术语准确的英文。
4. **Given** 某语言缺失某静态键, **When** 渲染该处文案, **Then** 回退展示默认语言（简体中文）文案而非键名。

---

### User Story 3 - 后台支付方式多语言配置 (Priority: P1)

运营人员在管理后台编辑支付方式时，展示名（`methodName`）与描述（`description`）各提供三个语言输入框（简体中文 / 繁体中文 / 英文），分别录入对应语言文案；三种语言均为必填，未填写完整不允许保存。收银台按下单语言展示对应支付方式名称与描述。

**Why this priority**: 支付方式名称是付款人选择支付方式时的核心可见文案，若不随语言变化则国际化不完整；用户明确要求后台支持多语言录入。

**Independent Test**: 在后台为某支付方式录入三语展示名与描述并保存；分别用三种 `language` 下单，验证收银台展示对应语言的支付方式名称与描述；故意只填两种语言时保存被拒绝并提示。

**Acceptance Scenarios**:

1. **Given** 后台支付方式编辑表单, **When** 打开展示名与描述编辑区, **Then** 各显示简体中文、繁体中文、英文三个输入框。
2. **Given** 三语展示名与描述均已填写, **When** 保存, **Then** 保存成功并三语文案均持久化。
3. **Given** 仅填写部分语言（缺繁体或英文）, **When** 保存, **Then** 保存被拒绝并给出明确校验提示，数据不落库。
4. **Given** 某支付方式已配置三语, **When** 付款人以 `language=zh-TW` 进入收银台, **Then** 该支付方式以繁体名称与描述展示。

---

### User Story 4 - 门户页面语言自适应与切换 (Priority: P2)

不绑定订单的门户页面（商户登录、入驻申请、入驻结果查询）首次访问时按浏览器语言自动判定语言，并提供手动语言切换器供用户在三种语言间切换，选择持久化于浏览器本地。

**Why this priority**: 这些页面无订单上下文，需独立的语言决定机制；提升商户侧可用性，但不阻断付款人核心支付流程。

**Independent Test**: 在英文浏览器首次打开登录页验证默认英文；通过切换器切到繁体并刷新，验证仍为繁体。

**Acceptance Scenarios**:

1. **Given** 浏览器语言为英文且用户未做过选择, **When** 打开门户页面, **Then** 页面默认英文展示。
2. **Given** 门户页面, **When** 用户通过切换器选择繁体中文, **Then** 当前页面文案立即切换且选择被持久化，刷新后保持。

---

### User Story 5 - 语言与页面元数据同步 (Priority: P2)

界面语言确定（订单页由下单参数、门户页由判定/切换）后，浏览器标签页标题（路由 title）与文档语言属性（`<html lang>`）随之与当前语言一致。

**Why this priority**: 提升可访问性与一致性体验，但不阻断核心流程。

**Independent Test**: 切换/进入不同语言后，检查标签页标题与 `document.documentElement.lang` 与当前语言一致。

**Acceptance Scenarios**:

1. **Given** 当前语言为英文, **When** 进入收银台路由, **Then** 标签页标题为英文且 `<html lang>` 为 `en`。
2. **Given** 当前语言为繁体中文, **When** 页面渲染, **Then** `<html lang>` 为 `zh-TW`。

---

### Edge Cases

- 下单接口 `language` 缺失或为非白名单值时，收银台回退默认简体中文，且不抛出阻断性错误。
- 门户页 `localStorage` 存在历史/非法语言值或被禁用时，回退默认简体中文，当前会话内切换仍生效（仅丢失持久化）。
- 静态文案某语言键缺失时回退默认简体中文，不显示键名。
- 后台保存支付方式时若三语未填全，保存被拒绝，已填内容不部分落库。
- 带占位符文案（如 `支付剩余 {time}`、`{min} 分 {sec} 秒`）在三语下占位符保留且正确插值。
- 金额、日期/时间格式化按当前语言区域正确呈现。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 下单接口必须新增展示语言参数 `language`，取值为受支持的语言标识（`zh-CN` / `zh-TW` / `en-US`）。
- **FR-002**: 收银台订单相关页面（PC/H5 收银台、电子收据）必须以下单接口传入的 `language` 决定展示语言，且不得提供用户可见的语言切换控件。
- **FR-003**: 当下单 `language` 缺失或为非受支持值时，系统必须回退到默认语言简体中文（`zh-CN`）。
- **FR-004**: 系统必须为繁体中文（`zh-TW`）提供与简体中文、英文键完全对齐的完整前端语言包。
- **FR-005**: 系统必须确保收银台全部用户可见静态文本（含 PC/H5 收银页、二维码弹窗、支付结果、电子收据、登录、入驻申请、入驻结果查询、错误/提示消息、路由标题、支付方式与渠道展示名）均通过国际化机制取文案，不残留硬编码语言文本。
- **FR-006**: 切换/确定语言后，系统必须使 Element Plus 组件库内置文案（按钮、弹窗、表单校验等）与当前语言一致。
- **FR-007**: 系统必须使浏览器标签页标题与文档语言属性（`<html lang>`）与当前语言同步。
- **FR-008**: 当前端静态文案某语言键缺失时，系统必须回退默认语言（简体中文）展示，不得显示原始键名。
- **FR-009**: 带占位符/复数的静态文案在三种语言下必须保持占位符一致并正确插值。
- **FR-010**: 后台支付方式管理必须支持对展示名（`methodName`）与描述（`description`）按简体中文、繁体中文、英文三种语言分别录入，编辑界面为每个字段提供三个语言输入框。
- **FR-011**: 后台保存支付方式时，三种语言的展示名与描述均为必填；任一语言缺失时必须拒绝保存并给出明确校验提示，且不部分落库。
- **FR-012**: 支付方式多语言文案必须存储在 `admin_payment_methods`（admin 前缀）表的 per-language 列中（展示名与描述各三列），不新增独立翻译表。
- **FR-013**: 收银台必须按下单 `language` 展示对应语言的支付方式名称与描述。
- **FR-014**: 门户页面（登录、入驻申请、入驻结果查询）必须在用户未选择时按浏览器语言自动判定语言，并提供可手动切换三种语言的控件，所选语言持久化于浏览器本地。
- **FR-015**: 语言相关持久化仅存储非敏感的语言标识，不得记录用户身份或支付敏感信息。

### Key Entities *(include if feature involves data)*

- **语言选项（Locale Option）**: 可选界面语言，关键属性为语言标识（`zh-CN` / `zh-TW` / `en-US`）与展示名称（简体中文 / 繁體中文 / English）。
- **前端语言包（Locale Message Bundle）**: 某语言下全部前端静态文案键值集合；三种语言键集合必须一致。
- **下单语言参数（Order Display Language）**: 商户在创建订单时传入的展示语言标识，决定该订单收银台/收据页语言。
- **支付方式多语言文案（Payment Method Localized Text）**: 支付方式展示名与描述在三种语言下的文案，存储于 `admin_payment_methods` 的 per-language 列，三语均必填。
- **门户语言偏好（Portal Locale Preference）**: 门户页面用户在浏览器本地保存的语言标识，用于持久化与回显。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 商户以三种 `language` 分别下单，收银台与收据页在 1 秒内以对应语言完成渲染，正确率 100%。
- **SC-002**: 在三种语言下遍历全部收银台页面与弹窗，未翻译文案/键名泄漏数量为 0。
- **SC-003**: 三种语言的前端语言包键集合 100% 对齐（无任一语言缺键或多键）。
- **SC-004**: 收银台订单页不存在任何用户可见语言切换控件（核查通过率 100%）。
- **SC-005**: 后台为支付方式录入三语展示名与描述后，收银台按下单语言展示对应文案的正确率 100%；仅填部分语言时保存被拒绝的拦截率 100%。
- **SC-006**: 门户页面浏览器语言自动判定（简体/繁体/英文样本）准确率 100%，且切换后刷新保持一致成功率 100%。
- **SC-007**: 收银台关键支付流程（下单→选择支付方式→拉起支付→结果展示）在三种语言下均可顺利完成，无因国际化导致的阻断性错误。

## Assumptions

- 受支持语言标识固定为 `zh-CN`（简体中文）、`zh-TW`（繁体中文，采用台湾地区常用用词与字形）、`en-US`（英文）；本期不引入其它语言。
- 下单接口语言参数名为 `language`，取值为上述标识；缺失或非法值统一回退 `zh-CN`。
- 后端返回的动态业务文案（如服务端错误消息）本期沿用现有处理方式，不要求按语言多版本返回；前端仅对自身可控静态文案与已配置的支付方式文案做国际化。
- 复用现有 `vue-i18n` 与 Element Plus 国际化能力，无需引入新国际化框架。
- 门户页语言偏好沿用现有 `localStorage` 键 `payflow-cashier-locale` 持久化。
- 多语言仅覆盖支付方式的展示名与描述；支付渠道名称等其它后台配置不在本期范围。
- 多语言文案以 per-language 列存储于 `admin_payment_methods`，不新增独立翻译表。
- 品牌名"PonyFlux Pay"作为商标在各语言下保持原样，不翻译。
- 后端管理接口与下单接口的变更继续遵循统一 `{code,message,data}` 响应规范。
