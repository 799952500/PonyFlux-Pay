# Feature Specification: 银联支付渠道完整接入

**Feature Branch**: `002-unionpay-channel`  
**Created**: 2026-05-12  
**Status**: Draft  
**Input**: User description: "我需要新增一个支付渠道，这个渠道的名称是银联支付，请根据项目要求写出规格文档"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 商户通过银联H5收银 (Priority: P1)

商户希望用户在移动端网页上通过银联云闪付完成支付。用户在商户的H5页面选择银联支付后，系统调起银联支付页面（或云闪付App），用户完成付款后返回商户页面并看到支付结果。

**Why this priority**: H5支付是移动端最通用的支付方式，不依赖App安装，覆盖所有银联持卡人用户。当前系统已有UNION_H5占位，是银联渠道的核心价值交付。

**Independent Test**: 可通过商户H5收银页面发起一笔银联支付订单，在银联沙箱环境完成支付，验证订单状态更新为"已支付"。

**Acceptance Scenarios**:

1. **Given** 商户已配置银联支付账号且渠道已启用，**When** 用户在收银台选择"银联云闪付"并确认支付，**Then** 系统返回银联支付页面URL，用户浏览器重定向到银联支付页面
2. **Given** 用户已在银联支付页面完成付款，**When** 银联发送异步支付成功通知到系统，**Then** 系统验证通知签名通过，更新订单为"已支付"并通知商户
3. **Given** 用户发起支付但未完成付款，**When** 订单超时（默认15分钟），**Then** 订单状态变更为"已关闭"，用户可重新发起支付

---

### User Story 2 - 商户通过银联扫码收银 (Priority: P2)

商户需要在PC收银台或线下场景通过银联二维码收款。系统生成银联二维码后，用户使用云闪付App扫码完成支付。

**Why this priority**: 扫码支付是在线商户PC端收银和线下扫码场景的刚需，覆盖Web端用户和线下商户场景，是银联渠道的第二大使用场景。

**Independent Test**: 在PC收银台发起银联扫码支付订单，系统返回二维码（或二维码链接），使用银联沙箱扫码测试工具完成支付，验证订单已支付。

**Acceptance Scenarios**:

1. **Given** 商户已配置银联支付账号，**When** 用户在PC收银台选择"银联扫码支付"，**Then** 系统生成支付二维码并展示给用户（含有效期内倒计时）
2. **Given** 支付二维码已展示且未过期，**When** 用户使用云闪付App扫码完成支付，**Then** 系统收到异步通知后更新订单状态为"已支付"
3. **Given** 支付二维码已过期（超过有效期），**When** 用户扫码，**Then** 银联返回二维码已过期，用户需重新生成

---

### User Story 3 - 商户对银联订单进行退款 (Priority: P2)

商户需要在后台对已支付的银联订单发起全额或部分退款，退款金额原路返回用户支付账户。

**Why this priority**: 退款是支付业务的基本闭环操作，是商户运营的必要功能。与P2扫码支付同优先级，因为两者都是完整支付渠道的必要组成部分。

**Independent Test**: 对一笔已支付的银联订单通过管理后台发起退款，验证退款申请提交成功，银联异步通知退款结果后系统更新退款状态。

**Acceptance Scenarios**:

1. **Given** 存在一笔已支付的银联订单，**When** 商户在管理后台对该订单发起全额退款，**Then** 系统向银联提交退款申请并创建退款记录（状态为"处理中"）
2. **Given** 退款申请已提交至银联，**When** 银联异步通知退款成功，**Then** 系统验证通知签名，更新退款状态为"已退款"，订单状态为"已退款"
3. **Given** 存在一笔已支付的银联订单，**When** 商户发起部分退款（退款金额小于支付金额），**Then** 系统提交部分退款申请，退款成功后订单状态保持"已支付"（支持多次部分退款）

---

### User Story 4 - 银联账单下载与对账 (Priority: P3)

系统需要每日自动下载银联渠道的账单文件，与本地支付记录进行对账，发现差异记录并生成对账报告。

**Why this priority**: 对账是支付系统资金安全的基础保障，但属于后台运营功能，可在核心支付流程稳定后再完善。

**Independent Test**: 触发银联渠道对账任务，系统下载前一日的银联账单，与本地支付记录逐笔比对，生成对账结果（成功/差异/失败）。

**Acceptance Scenarios**:

1. **Given** 银联渠道前一日有交易记录，**When** 对账任务在T日执行T-1日对账，**Then** 系统成功下载银联账单文件并解析为结构化记录
2. **Given** 账单已解析完成，**When** 系统逐笔比对账单记录与本地支付记录，**Then** 生成对账结果：完全匹配的记录数、银联独有记录数、本地独有记录数、金额不一致记录数
3. **Given** 对账发现差异记录，**When** 对账完成，**Then** 系统生成差异报告（记录差异类型和详情），支持人工审核处理

---

### User Story 5 - 商户配置银联支付账号 (Priority: P1)

商户管理员需要在管理后台配置银联支付账号参数（商户号、证书、密钥等），并启用银联支付渠道，使其在前端收银台可用。

**Why this priority**: 渠道配置是所有支付功能的前置条件，无配置则无法使用任何银联支付功能。

**Independent Test**: 在管理后台创建银联支付账号配置，填写必需的银联商户参数，启用渠道和路由，验证收银台展示银联支付选项。

**Acceptance Scenarios**:

1. **Given** 管理员已登录管理后台，**When** 在渠道管理中创建银联支付账号并填写商户号、证书路径、签名密钥等参数，**Then** 系统保存配置并验证连接性（可选健康检查）
2. **Given** 银联支付账号已创建且启用，**When** 管理员为商户配置银联渠道路由，**Then** 商户收银台展示银联支付选项
3. **Given** 银联支付账号已配置，**When** 管理员禁用该账号或路由，**Then** 收银台不再展示银联支付选项

---

### Edge Cases

- 当银联支付页面回调时用户关闭浏览器，系统如何确保订单状态最终一致？（依赖异步通知补偿）
- 当异步通知延迟到达（超过订单超时时间），订单已关闭但用户已付款，系统如何处理？（记录异常，支持人工处理退款）
- 当银联证书过期时，支付请求如何处理？（返回明确错误码，通知管理员更新证书）
- 当同一笔订单收到重复的支付成功通知时，系统如何幂等处理？（基于订单号或流水号去重）
- 当退款申请超时未收到银联结果通知时，系统如何处理？（支持主动查询退款结果）
- 当网络波动导致银联API调用超时，系统的重试和超时策略是什么？（不重试下单以免重复支付，通知接口依赖银联重试）

## Requirements *(mandatory)*

### Functional Requirements

**支付核心**

- **FR-001**: 系统 MUST 支持银联H5支付，用户在移动端浏览器中调起银联支付页面完成付款
- **FR-002**: 系统 MUST 支持银联扫码支付（QR），生成银联二维码供用户使用云闪付App扫码付款。首期支付方式范围：H5支付 + 扫码支付(QR)，不包含App支付和WAP支付
- **FR-003**: 系统 MUST 对银联异步支付通知进行签名验证，确保通知来源可信
- **FR-004**: 系统 MUST 支持支付幂等性，同一订单号不可重复发起支付（已有通用幂等机制，需确认对银联渠道有效）
- **FR-005**: 系统 MUST 在银联支付成功后，按现有回调规范通知商户系统（复用已有商户回调机制）
- **FR-006**: 系统 MUST 在银联支付失败（余额不足、超时、用户取消等）时，返回明确的错误描述给前端展示

**退款**

- **FR-007**: 系统 MUST 支持对已支付的银联订单发起全额退款
- **FR-008**: 系统 MUST 支持对已支付的银联订单发起部分退款
- **FR-009**: 系统 MUST 处理银联退款异步通知，更新退款状态
- **FR-010**: 系统 MUST 在退款申请失败时，允许商户重新发起退款

**配置管理**

- **FR-011**: 系统 MUST 支持管理员在后台配置银联支付账号参数（含商户号、证书、签名密钥等）
- **FR-012**: 系统 MUST 支持管理员启用/禁用银联支付渠道
- **FR-013**: 系统 MUST 支持管理员为不同商户配置独立的银联支付账号和路由

**对账**

- **FR-014**: 系统 MUST 支持自动下载银联T-1日账单文件
- **FR-015**: 系统 MUST 支持解析银联账单格式，并与本地支付记录进行比对
- **FR-016**: 系统 MUST 生成银联渠道对账差异报告（标识渠道独有、本地独有、金额不一致、状态不一致等差异类型），支持人工审核处理。对账功能纳入首期MVP，与支付/退款同步交付

**监控与运维**

- **FR-017**: 系统 MUST 记录银联API调用的请求和响应日志（脱敏处理敏感字段），用于问题排查
- **FR-018**: 系统 MUST 在银联API调用失败或证书即将过期时，通过日志或管理后台预警

### Key Entities

- **银联支付账号配置 (UnionPay Account Config)**: 商户的银联商户号、签名证书、签名密钥、银联网关地址、回调通知URL等参数，关联到商户和渠道配置体系
- **银联支付记录 (UnionPay Payment)**: 每笔银联交易的记录，包含银联交易流水号、订单号、支付金额、支付方式（H5/QR）、支付状态等
- **银联退款记录 (UnionPay Refund)**: 每笔银联退款的记录，包含退款单号、原交易流水号、退款金额、退款状态（处理中/已退款/失败）等
- **银联账单记录 (UnionPay Bill Record)**: 银联账单中的交易明细，包含交易时间、交易金额、交易类型、手续费等，用于与本地支付记录对比
- **支付方式 (Payment Method)**: 银联渠道下支持的支付方式（如H5支付、扫码支付等），每种方式有独立的编码、名称和启用状态

## Clarifications

### Session 2026-05-12

- Q: 支付渠道模块应该如何组织？ → A: 新增 `payflow-payment-channels` 父级聚合模块，将所有渠道子模块（wechat、alipay、union 及未来新增渠道）统一收纳在其下，代替当前渠道模块平铺在根目录的结构
- Q: 现有 wechat、alipay 模块是否需要在本次一并迁移？ → A: 本次一并迁移，wechat、alipay、union 三个渠道模块全部迁入 `payflow-payment-channels` 父模块下，形成完整统一结构
- Q: 模块迁移是否允许改动依赖这些模块的外部配置？ → A: 允许同步更新所有引用（根POM、cashier-server依赖、CI/CD脚本等），一次性完成迁移，不留向后兼容占位

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 商户可在5分钟内完成银联支付账号的后台配置（从进入配置页到保存成功）
- **SC-002**: 用户从点击"确认支付"到看到支付结果页面（或跳转到银联支付页）的等待时间不超过3秒
- **SC-003**: 银联异步通知处理成功率不低于99.5%（排除银联侧未发送通知的异常情况）
- **SC-004**: 银联支付下单成功率达到99%以上（在银联服务可用且配置正确的前提下）
- **SC-005**: 退款申请提交成功率达到99%以上（在银联服务可用且配置正确的前提下）
- **SC-006**: 银联渠道对账自动完成率不低于95%（在账单文件可正常下载的前提下）
- **SC-007**: 所有银联API交互出现异常时，系统能在30秒内输出可定位问题的日志
- **SC-008**: 银联渠道上线后，支持日均1000笔以上支付交易而系统无性能降级

## Assumptions

- 银联开放平台提供标准的API接口文档和沙箱测试环境，接口规范遵循银联官方最新版本
- 商户已具备银联开放平台的注册账号，并能获取商户号、证书和签名密钥
- 银联异步通知机制与现有微信/支付宝回调机制类似（HTTP POST + 签名验证），无需引入全新的通知模式
- 银联账单文件格式为CSV或固定宽度的结构化文本，可通过现有账单解析框架进行适配
- 银联渠道的证书管理沿用项目现有的文件存储方案（非云密钥管理服务）
- 本规格仅覆盖境内人民币支付场景，暂不涉及跨境支付和外币结算
- 前端收银台UI已有银联支付方式的占位，仅需对接后端接口即可展示
- 银联支付不涉及分账、营销优惠券等高级功能，仅覆盖基础收单和退款
- 本次实施将创建 `payflow-payment-channels` 父级聚合模块，将现有 `payflow-payment-wechat`、`payflow-payment-alipay`、`payflow-payment-union` 一次性迁移为其子模块，同步更新根POM、cashier-server依赖声明及CI/CD脚本中所有模块路径引用，未来新增渠道均在该父模块下新增子模块
