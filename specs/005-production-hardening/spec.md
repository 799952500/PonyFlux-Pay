## User Scenarios & Testing *(mandatory)*

### User Story 1 - 系统管理员安全管控 (Priority: P1)

系统管理员需要确保管理后台的所有操作都经过严格的身份认证和权限校验，防止未授权访问导致的数据泄露或恶意操作。当前系统存在三个严重问题：商户管理接口完全没有鉴权（任何人均可枚举/创建/删除商户）、JWT 签名密钥硬编码在源代码中（攻击者获取源码即可伪造任意 Token）、所有管理员角色拥有相同的增删改权限（无角色级授权区分）。

**Why this priority**: 这是系统最基础的安全防线。未鉴权的商户接口意味着攻击者可以获取所有商户的 HMAC 签名密钥，进而伪造任意商户的支付请求。不修复这些问题，系统无法通过任何安全审计，不具备商用资格。

**Independent Test**: 通过自动化安全测试验证——未携带 Token 请求 `/api/v1/merchants/*` 应返回 401；携带低权限角色 Token 请求创建管理员用户应返回 403；部署时未设置 `JWT_SECRET` 环境变量应导致服务启动失败。

**Acceptance Scenarios**:

1. **Given** 未认证用户，**When** 访问 `/api/v1/merchants` 任意接口，**Then** 返回 401 Unauthorized
2. **Given** 持有 `ADMIN` 角色（非 `SUPER_ADMIN`）Token 的用户，**When** 尝试创建新管理员用户或修改系统配置，**Then** 返回 403 Forbidden
3. **Given** 服务启动时 `JWT_SECRET` 环境变量未设置或无有效值，**When** 服务启动，**Then** 启动失败并给出明确的错误提示
4. **Given** 管理员查看商户信息，**When** 调用商户详情接口，**Then** 返回数据中不包含 `merchantKey`（HMAC 签名密钥）字段

### User Story 2 - 支付数据完整性保障 (Priority: P1)

支付系统必须确保每一笔交易数据的完整性和一致性。当前系统存在多个数据完整性缺陷：订单支付成功后 `payAmount`（实付金额）字段始终为 0；退款金额校验存在竞态条件（两个并发退款请求可能合计超过原支付金额）；对账查询引用了不存在的数据库列名。

**Why this priority**: 实付金额为 0 直接影响财务报表和对账准确性；退款超额是直接的资损漏洞；对账 SQL 报错会导致对账功能完全不可用。

**Independent Test**: 完成一笔支付后查询订单详情，`payAmount` 应正确显示实际支付金额；并发发送两个各 60 元的退款请求（原支付 100 元），第二个请求应被拒绝；调用对账聚合接口应正常返回退款统计数据。

**Acceptance Scenarios**:

1. **Given** 一笔金额为 10000 分（100 元）的订单，**When** 支付成功回调到达，**Then** 订单 `payAmount` 更新为 10000（而非 0）
2. **Given** 一笔 100 元已支付订单，**When** 同时发起两笔 60 元退款，**Then** 仅一笔成功，另一笔因超额被拒绝
3. **Given** 存在退款记录，**When** 调用 Dashboard 聚合刷新接口，**Then** 退款金额正确聚合统计（不报 SQL 错误）
4. **Given** 订单到期扫描器正在运行，**When** 支付回调同时到达，**Then** 订单状态正确变为 PAID（不被扫描器错误覆盖为 EXPIRED）

---

### User Story 3 - 支付回调安全验证 (Priority: P1)

支付渠道（支付宝/微信/银联）的异步回调是支付流程的关键环节。当前支付宝回调验签逻辑仅检查了签名字段是否为空，未实际验证签名与支付宝公钥的匹配性。任何能够向回调端点发送 HTTP 请求的攻击者都可以伪造支付成功通知。

**Why this priority**: 这是可直接造成资损的漏洞——攻击者伪造回调即可让系统认为订单已支付，从而获得商品或服务却不实际付款。

**Independent Test**: 向支付宝回调端点发送签名无效的模拟通知，系统应拒绝并返回验签失败；发送正确签名的通知，系统应正常处理。

**Acceptance Scenarios**:

1. **Given** 支付宝异步通知端点收到请求，**When** 签名验证失败（签名与支付宝公钥不匹配），**Then** 返回验签失败响应，订单状态不变
2. **Given** 支付宝异步通知端点收到请求，**When** 请求体缺少签名字段，**Then** 返回参数错误响应
3. **Given** 支付成功通知签名验证通过，**When** 处理支付结果，**Then** 订单状态正确更新为 PAID

---

### User Story 4 - 服务高可用与容错 (Priority: P1)

系统在依赖服务（Redis、MySQL、Admin 服务）不可用或响应缓慢时，必须具备合理的降级和容错能力。当前系统存在多个单点故障风险：HTTP 客户端未配置连接/读取超时（下游慢响应会导致线程永久阻塞）、Redis 不可用时所有安全拦截器静默放行（fail-open）、数据库连接池使用默认配置（无生产调优）。

**Why this priority**: 生产环境中依赖服务故障是常态而非异常。超时缺失会导致线程池耗尽和级联故障；fail-open 意味着攻击者可以通过 DDoS 攻击 Redis 来绕过所有安全控制。

**Independent Test**: 模拟 Admin 服务延迟 10 秒，cashier 应在配置的超时时间内返回降级响应而非永久挂起；模拟 Redis 不可用，支付请求应返回"服务暂不可用"而非绕过限流和幂等检查。

**Acceptance Scenarios**:

1. **Given** Admin 服务响应超时（超过配置阈值），**When** Cashier 请求支付方式配置，**Then** 在 5 秒内返回缓存或降级数据，不阻塞调用线程
2. **Given** Redis 不可用，**When** 商户发起支付请求，**Then** 系统返回明确的服务不可用错误（而非绕过幂等和限流检查静默放行）
3. **Given** 服务收到 Kubernetes SIGTERM 信号，**When** 执行优雅关闭，**Then** 等待进行中的请求完成（最长 30 秒）后再关闭进程
4. **Given** 支付路由账户在数据库中被禁用，**When** 下一次路由选择发生，**Then** 被禁用的账户不再收到流量（路由注册表在 5 分钟内自动刷新）

### User Story 5 - 商户生命周期管控 (Priority: P2)

管理员暂停或关闭某商户后，该商户必须立即停止所有支付能力。当前系统的问题在于：商户登录接口会检查状态并拒绝非 ACTIVE 商户，但支付创建接口完全未检查商户状态——被暂停的商户只要持有有效的 API 密钥就仍可正常收款。

**Why this priority**: 商户管控失效意味着平台无法有效执行风控措施。如果某商户因违规被暂停，但其仍可通过 API 继续收款，平台将面临合规和资金风险。

**Independent Test**: 在后台将某商户状态设为 SUSPENDED，使用该商户的 API 密钥发起支付请求，应被拒绝并返回"商户已暂停"错误。

**Acceptance Scenarios**:

1. **Given** 某商户状态为 SUSPENDED，**When** 使用其密钥发起创建订单请求，**Then** 返回错误码表明商户不可用
2. **Given** 某商户状态为 SUSPENDED，**When** 使用其密钥发起退款请求，**Then** 返回错误码表明商户不可用
3. **Given** 管理员将商户从 ACTIVE 变更为 SUSPENDED，**When** 变更保存到数据库，**Then** 该商户现有未支付订单仍可按正常流程过期处理

---

### User Story 6 - 密钥与凭证安全管理 (Priority: P2)

所有支付渠道的 API 密钥、商户 HMAC 签名密钥、数据库密码等敏感凭证必须安全存储，不得以明文形式出现在代码、配置文件、API 响应或日志中。当前系统在多个层面存在密钥泄露问题：商户 `merchantKey` 和渠道 `appSecret`/`mchKey` 明文存储在数据库并直接在 API 响应中返回；两个服务硬编码了相同的默认内部通信 Token；商户签名密钥硬编码在配置文件和测试工具类中。

**Why this priority**: 密钥泄露是支付系统最致命的安全问题之一。攻击者获取商户签名密钥后可以伪造任意商户的合法请求；获取渠道密钥后可以操作支付渠道账户。

**Independent Test**: 验证所有 API 响应中不包含 `merchantKey`、`appSecret`、`mchKey`、`certPassword` 等敏感字段；验证配置文件中的默认密钥值已被环境变量引用替代。

**Acceptance Scenarios**:

1. **Given** 管理员查询商户详情，**When** API 返回商户数据，**Then** 响应中不包含 `merchantKey` 字段（即使数据库中存储了该值）
2. **Given** 管理员查询渠道账户列表，**When** API 返回账户数据，**Then** 响应中不包含 `appSecret`、`mchKey`、`certPassword` 字段
3. **Given** 部署生产环境，**When** 未显式设置 `INTERNAL_TOKEN` 环境变量，**Then** 服务启动失败（不接受默认值 `dev-payflow-internal-token` 用于生产）
4. **Given** 渠道账户创建或更新时传入 `appSecret`，**When** 存储到数据库，**Then** 该值以 AES-256-GCM 加密形态存储（而非明文）

### User Story 7 - Webhook 通知投递 (Priority: P2)

支付成功后系统必须向商户发送 Webhook 通知（HTTP 回调商户指定的 notifyUrl），告知其订单支付结果。当前 `WebhookDispatchService` 是一个空实现（仅打印日志），导致商户永远收不到支付成功通知，必须依赖主动轮询查询订单状态。

**Why this priority**: Webhook 通知是支付系统的核心功能之一。没有 Webhook，商户无法实时感知支付结果，严重影响用户体验和业务流程。虽然商户可以通过查询接口获取状态，但这不是实时的，增加了商户侧的延迟和复杂度。

**Independent Test**: 配置一个测试 HTTP 端点作为商户 notifyUrl，完成一笔支付后，验证测试端点收到包含订单信息的 HTTP POST 请求。

**Acceptance Scenarios**:

1. **Given** 商户配置了 notifyUrl，**When** 一笔支付完成，**Then** 系统在 1 分钟内至少向该 URL 发送一次 HTTP POST 通知
2. **Given** 首次通知失败（目标 URL 返回非 2xx 或超时），**When** 重试机制启动，**Then** 按递增间隔（1 分钟、5 分钟、15 分钟、30 分钟、1 小时）重试最多 5 次
3. **Given** 商户未配置 notifyUrl，**When** 支付完成，**Then** 不发送通知（不报错）

---

### User Story 8 - 防刷与暴力破解防护 (Priority: P2)

系统必须有效防御恶意请求——包括撞库/暴力破解商户密码、利用时间窗口突发的 API 请求、通过 CSV 导出注入恶意公式等攻击手段。当前商户登录无频率限制（可无限尝试），速率限制使用固定窗口算法（在分钟边界可被绕过），CSV 导出未过滤公式注入字符。

**Why this priority**: 登录接口无频率限制意味着攻击者可以无限尝试密码；CSV 注入可能用于社会工程攻击窃取管理员凭证；这些都是 OWASP Top 10 中强调的安全风险。

**Independent Test**: 连续 10 次使用错误密码登录同一商户账户，第 11 次应在锁定时间内被拒绝；导出的 CSV 文件中，以 `=`、`+`、`-`、`@` 开头的单元格内容应被转义为文本格式。

**Acceptance Scenarios**:

1. **Given** 某商户账户在 5 分钟内登录失败 5 次，**When** 第 6 次尝试登录（即使是正确密码），**Then** 返回"账户已锁定，请 15 分钟后重试"
2. **Given** 订单数据中包含 `=HYPERLINK("http://evil.com")` 格式的商户订单号，**When** 导出订单 CSV，**Then** 该单元格以单引号前缀转义为纯文本（`'=HYPERLINK(...)`）
3. **Given** 商户 API 请求正常进行，**When** 在 1 秒内突增到正常流量的 10 倍，**Then** 超出限额的请求返回限流错误而非穿透

### User Story 9 - 可观测性基础建设 (Priority: P3)

运维团队需要基本的可观测性能力来监控系统健康状态和排查生产问题——包括关键业务指标（支付成功率、渠道延迟）、请求链路追踪、自定义健康检查。当前系统只暴露了 Spring Boot 默认的 `/actuator/health` 和 `/actuator/info` 端点，没有任何业务指标或分布式追踪能力。

**Why this priority**: 生产环境没有可观测性意味着"盲飞"——无法在用户投诉之前发现支付成功率下降、渠道延迟飙升等问题。虽然不直接影响支付核心流程，但缺乏监控会导致故障发现和定位严重延迟。

**Independent Test**: 访问 `/actuator/metrics` 应返回包含支付相关自定义指标的 Prometheus 格式数据；某支付渠道不可用时，健康检查端点应报告该渠道为 DOWN。

**Acceptance Scenarios**:

1. **Given** 系统正常运行，**When** 访问指标端点，**Then** 返回支付成功率、各渠道调用次数和延迟分位数等业务指标
2. **Given** 某支付渠道（如支付宝）API 不可达，**When** 访问健康检查端点，**Then** 返回包含"支付宝渠道"状态为 DOWN 的详细信息
3. **Given** 一笔支付请求从 cashier 发起、经过路由选择、到达渠道处理，**When** 在各服务日志中查询该请求，**Then** 可通过统一的 Trace ID 串联完整调用链

---

### User Story 10 - 输入校验与数据规范 (Priority: P3)

所有用户输入必须在进入业务逻辑之前经过严格校验。当前系统多个控制器接受 `Map<String, Object>` 或实体对象直接作为请求体，绕过了声明式校验（`@Valid`），且核心实体类（Order、Payment、Refund）没有任何校验注解。此外，管理后台硬删除商户（而非软删除）可能导致历史数据引用断裂。

**Why this priority**: 输入校验是纵深防御的基础层。虽然当前的大部分输入来自经过认证的管理员，但防御深度原则要求在外层就拦截非法数据，而非依赖业务代码中的手动判断。

**Independent Test**: 发送包含负数金额的支付请求应被拒绝并返回校验错误；发送缺失必填字段（如 `subject`）的订单创建请求应返回明确的字段错误提示。

**Acceptance Scenarios**:

1. **Given** API 收到创建订单请求，**When** `subject` 为空或 `amount` 为非正数，**Then** 返回 400 并指明具体校验失败的字段
2. **Given** 管理员"删除"某商户，**When** 操作完成后查询数据库，**Then** 该商户记录被标记为 DELETED 状态（而非物理删除）
3. **Given** API 收到包含未知字段的 JSON 请求体，**When** 处理请求，**Then** 未知字段被忽略（不引发 500 错误）

### Edge Cases

- 并发支付与订单过期扫描同时触发时，PAID 状态必须优先于 CLOSED/EXPIRED
- 退款审批通过后执行时，需重新验证退款总额不超过原支付金额（审批期间可能有其他退款完成）
- 支付渠道回调重入（同一支付多次收到相同通知），系统必须幂等处理
- JWT Token 黑名单在 Redis 故障期间的行为：应拒绝而非放行（对安全关键路径采用 fail-close）
- 数据库主从延迟场景下，刚写入的订单立即查询可能查不到——需确保关键路径读主库
- 支付金额极端值：0 元金额、超过 Long.MAX_VALUE 分（天文数字）的金额
- 商户名称/订单标题包含 Emoji、特殊 Unicode 字符时的处理

## Requirements *(mandatory)*

### Functional Requirements

**安全认证与授权**：
- **FR-001**: 所有管理后台 API（包括 `/api/v1/merchants/*`）必须经过 JWT 认证拦截器，未认证请求返回 401
- **FR-002**: 系统必须实现基于角色的访问控制（RBAC）——SUPER_ADMIN 拥有全部权限，ADMIN 角色的增删改操作受限（不能创建管理员用户、不能修改系统全局配置、不能修改角色权限）
- **FR-003**: JWT 签名密钥和内部通信 Token 必须通过环境变量注入，生产环境不允许使用代码中的默认值（无有效环境变量时启动失败）
- **FR-004**: API 响应中不得包含敏感字段：`merchantKey`、`appSecret`、`mchKey`、`certPassword`——在序列化层统一过滤

**支付数据完整性**：
- **FR-005**: 支付成功后 `payAmount`（实付金额）必须更新为实际支付金额，不得为 0 或 null
- **FR-006**: 退款金额校验必须有并发保护——同时发起的多个退款请求，合计退款金额不得超过原支付金额
- **FR-007**: Dashboard 聚合查询中的退款统计（`aggregateRefunds`）必须引用正确的数据库列名
- **FR-008**: 订单过期扫描器与支付回调处理必须通过乐观锁（版本号或状态条件 UPDATE）防止状态覆盖

**支付回调安全**：
- **FR-009**: 所有支付渠道（支付宝、微信、银联）的异步回调必须验证签名——支付宝使用公钥验签、微信使用 APIv3 签名验证、银联使用 RSA-SHA256 验签
- **FR-010**: 回调验签失败时，系统必须拒绝处理并返回渠道要求的错误响应格式（如支付宝要求返回 "fail"）

**服务容错与高可用**：
- **FR-011**: 所有出站 HTTP 调用必须配置连接超时（不超过 5 秒）和读取超时（不超过 30 秒）
- **FR-012**: Redis 不可用时，幂等检查、限流检查和 JWT 黑名单检查必须进入 fail-close 模式（拒绝请求并返回服务不可用），而非 fail-open（跳过检查）
- **FR-013**: 支付路由账户注册表必须在数据库变更后 5 分钟内自动刷新，无需重启服务
- **FR-014**: 服务必须支持优雅关闭——收到终止信号后等待进行中请求完成（最长 30 秒）

**商户管控**：
- **FR-015**: 非 ACTIVE 状态（SUSPENDED、CLOSED）的商户不得创建新订单或发起支付
- **FR-016**: 非 ACTIVE 状态商户的未支付订单应在到期后自动失效（不退款、不通知）

**密钥安全**：
- **FR-017**: 数据库中存储的支付渠道 API 密钥（`appSecret`、`mchKey`）必须使用 AES-256-GCM 加密
- **FR-018**: 系统已有的 AES 加密组件（`AesEncryptor`）必须集成到数据持久层——加密在写入前、解密在读取后自动进行
- **FR-019**: 生产配置文件中的商户签名密钥必须移除，仅通过环境变量或外部密钥管理服务获取

**Webhook 通知**：
- **FR-020**: 支付成功后必须向商户配置的 `notifyUrl` 发送 HTTP POST 通知，携带订单 ID、支付金额、支付状态等关键信息
- **FR-021**: 通知失败时必须自动重试（递增间隔），重试仍失败的记录必须持久化并支持人工补发

**防刷与安全防护**：
- **FR-022**: 商户登录必须实施频率限制（单账户 5 分钟内最多 5 次失败尝试，超出后锁定 15 分钟）
- **FR-023**: API 速率限制使用滑动窗口算法替代固定窗口算法
- **FR-024**: 所有 HTTP 响应必须包含安全头：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Strict-Transport-Security`（HTTPS 场景）
- **FR-025**: CSV/Excel 导出功能必须过滤公式注入字符（以 `=`、`+`、`-`、`@` 开头的单元格内容添加单引号前缀转义）

**可观测性**：
- **FR-026**: 系统必须暴露支付成功率、各渠道调用耗时（P50/P95/P99）、退款率等核心业务指标
- **FR-027**: 所有服务间调用必须传递统一的 Trace ID，支持跨服务日志关联
- **FR-028**: 健康检查端点必须包含对关键外部依赖（MySQL、Redis、各支付渠道 API）的连通性检测

**数据规范**：
- **FR-029**: 所有接收用户输入的请求体必须使用强类型 DTO + `@Valid` 校验注解，替换 `Map<String, Object>` 原始参数
- **FR-030**: 核心业务实体（Order、Payment、Refund、Merchant）的关键字段必须添加 `@NotNull`/`@NotBlank`/`@Min` 等校验注解
- **FR-031**: 商户删除操作必须使用软删除（状态标记为 DELETED），禁止物理删除

### Key Entities

- **SensitiveFieldFilter**: API 序列化层的敏感字段过滤规则——定义哪些实体类型的哪些字段在序列化时需排除或脱敏
- **WebhookRecord**: Webhook 通知投递记录——关联订单 ID、目标 URL、投递状态、重试次数、下次重试时间
- **MerchantStatus**: 商户状态枚举增强——明确状态转移规则（ACTIVE→SUSPENDED→ACTIVE 允许，ACTIVE→CLOSED 不可逆，CLOSED 不可恢复）
- **TraceContext**: 跨服务请求追踪上下文——包含 Trace ID、Span ID、上游服务标识

## Assumptions

- 当前系统运行在单一时区（Asia/Shanghai），国际化时区支持不在本次加固范围内
- 多币种支持不在本次范围内——系统假设人民币（CNY）为默认货币
- 数据库读写分离/主从延迟的处理不在本次范围内——假设为单主库部署
- 密钥管理服务（如 HashiCorp Vault、AWS KMS）的集成不在本次范围内——密钥通过环境变量和 AES 数据库加密保护
- 分布式追踪系统的选型和部署（Jaeger/Zipkin）由运维团队决定——本规范只要求在代码层面传递 Trace ID
- 现有兼容性视图（如 `merchants` → `admin_merchants`）保持不变，表重命名不在本次范围内
- 前端安全加固（CSP 头、XSS 防护等）已在 004-business-optimization 中部分覆盖，本次聚焦后端
